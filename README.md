# TeamSpeak Audio Control

Управление звуком трансляции **TeamSpeak 6** на Windows: выбор приложений,
фильтры по имени exe и отдельная громкость для каждого приложения.

Неофициальный независимый проект; не связан с разработчиками TeamSpeak.

[Скачать exe для Windows x64](https://github.com/gutjei/ts6-audio-control/releases/latest)
· [Статус сборки](https://github.com/gutjei/ts6-audio-control/actions/workflows/windows-release.yml)

Панель управления звуком трансляции TeamSpeak 6. Галочки и regexp меняют набор
источников в уже работающем потоке. Видеопоток и микрофон не переключаются.

## Возможности

- Список приложений с аудиосессиями и переключение захвата галочками.
- Общие include/exclude regexp по имени exe.
- Громкость 0–200% для каждого приложения, только в трансляции.
- Изменение правил и громкости во время шаринга.
- Автосохранение настроек по имени exe, независимо от PID.

## Готовое приложение

Скачай `TeamSpeakAudioControl.exe` из [Releases](https://github.com/gutjei/ts6-audio-control/releases/latest)
и запусти его. Установка Python, Frida и Visual Studio не требуется.
Нужны Windows 11 x64 и установленный TeamSpeak 6 x64. Exe не подписан цифровым
сертификатом; SHA-256 опубликован рядом с файлом в `SHA256SUMS.txt`.

Релизная версия сохраняет настройки в `%LOCALAPPDATA%\TS6AudioControl\settings.json`,
журналы — в подпапку `logs`. Обновление или перемещение exe не сбрасывает настройки.
Для переноса настроек исходной Python-версии положи её `settings.json` рядом с exe
**до первого запуска**. Уже сохранённые настройки релизной версии имеют приоритет.
Перед запуском exe закрой старую панель Python.

## Установка из исходников

Нужны Windows 11 x64, TeamSpeak 6 x64, Python 3.14 x64 с Tcl/Tk,
Visual Studio 2022 Build Tools с компонентом **Desktop development with C++**
и Windows SDK 10.0.26100.0. Это проверенная конфигурация проекта.
Сборочный скрипт автоматически находит Visual Studio через `vswhere`.

В PowerShell:

```powershell
git clone git@github.com:gutjei/ts6-audio-control.git
cd ts6-audio-control
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\build-native.cmd
```

Готовые DLL появятся в `build/audio_mixer.dll` и `build/audio_inventory.dll`. В Git хранятся исходники;
зависимости и результаты сборки устанавливаются локально. Перед повторной
сборкой закрой панель и TeamSpeak, чтобы Windows освободила загруженную DLL.

## Запуск

Двойной щелчок по `Start Audio Router.vbs` открывает панель без консоли.
Лаунчер предпочитает `.venv`, затем Python Launcher (`pyw`), затем `pythonw` из PATH.
Альтернатива из PowerShell: `.\.venv\Scripts\python.exe audio_router_gui.py`.

1. Запустить TeamSpeak и панель, нажать **Подключить**.
2. Один раз начать заново шаринг с захватом звука. Существовавший до подключения
   поток не перехватывается. Панель покажет количество управляемых потоков.
3. Выбирать приложения галочками, менять regexp или громкость. Шаринг больше перезапускать
   не нужно. Ручное изменение применяется обычно за 0,5–1 секунду; создание
   нового Windows AudioClient может занять дольше.

Запускай только одну панель одновременно. Для отключения закрой панель. Управляемый поток останется
тихим; для возврата стандартного захвата TS перезапустить шаринг.

## Правила

- Сопоставление с именем exe, без учёта регистра; синтаксис Python `re`.
- Include автоматически выбирает совпадающие приложения. Пустой include ничего
  не выбирает автоматически.
- Галочка задаёт ручное включение/выключение, перекрывая include.
- Exclude перекрывает include и ручное включение. TeamSpeak исключён всегда.
- «Сбросить ручной выбор» возвращает выбор к regexp.
- Некорректный regexp не применяется: остаются последние корректные правила.
- Настройки автоматически сохраняются в `settings.json`.
  В exe-версии файл находится в `%LOCALAPPDATA%\TS6AudioControl`, при запуске
  из исходников — в папке проекта.

## Громкость приложений

Выбрать строку приложения, затем передвинуть ползунок внизу окна. В колонке
«Уровень» отображается значение каждого приложения. Диапазон 0–200%: 0% — тишина,
100% — исходная громкость, больше 100% — усиление (громкие пики могут ограничиваться).
Кнопка «100%» возвращает исходный уровень выбранного приложения.

Уровни хранятся в `settings.json` в поле `volumes`, например
`"firefox.exe": 37`. Ключ — имя exe в нижнем регистре, **не PID**. После перезапуска
приложения, панели или Windows уровень применяется к новому процессу с этим именем;
несколько экземпляров одного exe получают одинаковый уровень. Старые настройки
без поля `volumes` загружаются с исходной громкостью 100%, regexp и галочки сохраняются.
Приложения с сохранённым уровнем остаются видимыми даже когда они не запущены.

Громкость применяется к аудиомиксу трансляции, не меняя системную громкость приложения.
Изменение уровня не пересоздаёт поток захвата. Сброс ручного выбора галочек не удаляет
сохранённые уровни. Громкость относится ко всему выбранному дереву процесса.

В списке видны приложения с активной или неактивной аудиосессией на любом
выходном устройстве, а также приложения с сохранённым ручным выбором или громкостью.
Остальные беззвучные процессы не перечисляются. Статус «активна» означает активную
сессию Windows, а не доказанное наличие слышимого сигнала. Список обновляется
автоматически по событиям; «Обновить аудиосессии» позволяет запросить обновление вручную.

## Как устроено

Frida подключается только к основному процессу TeamSpeak и перехватывает
`ActivateAudioInterfaceAsync` для `VAD\Process_Loopback`, вызванный TeamSpeak.dll.
Вместо общего системного звука базовый захват получает выделенный молчащий
процесс. Его пакеты дают тактирование. Поэтому снятие перехвата не подставляет
в текущий поток весь звук рабочего стола.

Нативная DLL создаёт отдельные WASAPI process-loopback потоки для разрешённых
деревьев процессов и смешивает PCM в `IAudioCaptureClient::GetBuffer`.
PCM не пересылается в Python/JS и не записывается на диск. Потоки выравниваются
по QPC в 100-нс единицах с дополнительным буфером 30 мс. Поддерживаются PCM16
и Float32, 1–8 каналов, 8–192 кГц. Пики суммы ограничиваются диапазоном PCM.
Метаданные/ошибки исходной версии записываются в `_local/logs/gui-router.jsonl`,
релизной — в `%LOCALAPPDATA%\TS6AudioControl\logs\gui-router.jsonl`.
Встроенная DLL распаковывается в подпапку `native/<sha256>` каталога настроек:
TeamSpeak может удерживать её после закрытия панели, поэтому она не хранится
во временной папке упаковщика. Разные сборки DLL не заменяют друг друга.

Backend ждёт события Core Audio и изменения настроек. Набор PID и громкостей
передаётся в микшер только при изменении итогового набора; после нового подключения
первая конфигурация передаётся обязательно. Проверка связи (`heartbeat`) и чтение
счётчиков выполняются отдельно раз в секунду, без пересылки правил и без перечисления
процессов или аудиосессий. При потере heartbeat более чем на 3 секунды выход микшера замолкает. Удалённый PID перестаёт участвовать в следующем пакете
после получения нового набора правил. Добавление требует активации источника
и заполнения буфера. Короткий щелчок/пауза при переключении возможны.

## Уведомления Windows и применение настроек

Нативный модуль `audio_inventory.dll` работает в панели, отдельно от DLL микшера:

- `IAudioSessionNotification` сообщает о новых аудиосессиях.
- `IAudioSessionEvents` сообщает об изменении состояния и отключении сессии.
- `IMMNotificationClient` сообщает об изменениях устройств; подписки перестраиваются
  для всех активных устройств воспроизведения.
- При запуске сначала регистрируются уведомления, затем считываются существующие
  сессии. Новые сессии сохраняются из callback с собственным COM-reference, чтобы
  не зависеть от полноты последующих перечислений Windows.
- Имена exe и родительские PID определяются через Toolhelp только по событиям
  сессий/устройств или завершению связанного процесса. Сохраняются лишь процессы
  с аудиосессиями и их предки, необходимые для захвата дерева.
- `RegisterWaitForSingleObject` сообщает о завершении связанных процессов,
  в том числе родительского процесса браузера без собственной аудиосессии.

Администратор и WMI не нужны. Нет периодического полного сканирования процессов.
Callback только ставит уведомление в очередь; работа с COM и освобождение подписок
выполняются на отдельном MTA-потоке. При ошибке наблюдения старый список разрешений
сбрасывается в тишину; кнопка обновления повторно создаёт подписки.

Изменения UI будят backend сразу после проверки и сохранения. Задержки ввода:
350 мс для regexp и 120 мс для громкости. Неизменившиеся строки таблицы не
перерисовываются.

Микшер использует `AUDCLNT_STREAMFLAGS_EVENTCALLBACK` и `SetEventHandle`:
каждый источник открывает и читает WASAPI на собственном MTA-потоке,
ожидающем только его аудиособытие или остановку. Для него запрашивается MMCSS
`Audio`; если приоритет недоступен, захват работает с обычным приоритетом.
Открытие нового приложения не задерживает чтение остальных. Управляющий поток
обрабатывает изменения правил, завершение источников, heartbeat и повторные
подключения. Нет `Sleep(4)` и обхода всех источников на каждом аудиособытии.
На выбранное дерево процесса приходится один поток захвата.
У каждого источника своя очередь с одним писателем и одним читателем (SPSC);
PCM публикуется целыми пакетами: атомарные индексы обновляются один раз на пакет,
а не на кадр. Общий mutex не удерживается при чтении, записи или смешивании PCM.
При переполнении отбрасывается входящий пакет, потребитель не блокируется.
Уже прочитанные кадры не воспроизводятся повторно, включая выход из mute.
Политика громкости публикуется неизменяемым снимком, без копирования карты
на каждом пакете. Буферы смешивания выделяются при создании контекста.
Короткая блокировка поиска контекста и синхронизация shared_ptr остаются;
это не полностью lock-free аудиотракт. Каждый источник генерирует свои события,
поэтому нагрузка зависит от количества источников.

Дополнительная задержка выравнивания — **30 мс** вместо 100 мс; это не полная
задержка трансляции TeamSpeak. Резерв очереди на две секунды не означает
двухсекундную задержку: кадры выбираются по QPC, а устаревшие отбрасываются.
30 мс — фиксированный запас, автоматическое увеличение не реализовано.
`RouterDiagnostics` возвращает число пробуждений захвата, запрошенных и
недостающих кадров источников и задержку в миллисекундах. Старт источника
и паузы тоже могут увеличивать счётчик недостающих кадров.

Используется подход [Windows-захвата OBS](https://github.com/obsproject/obs-studio/blob/master/plugins/win-wasapi/win-wasapi.cpp)
с отдельным событийным потоком и MMCSS, без RTWorkQ.
В OBS [размер блока — 1024 кадра](https://github.com/obsproject/obs-studio/blob/master/libobs/media-io/audio-io.h)
(около 21,3 мс при 48 кГц), а [буферизация](https://github.com/obsproject/obs-studio/blob/master/libobs/obs-audio.c)
может увеличиваться при отставании источников. Размер блока не равен полной
задержке OBS. Наш выход следует запросам TeamSpeak, поэтому планировщик OBS
и его адаптивная буферизация не перенесены.

Справка Microsoft: [новые сессии](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nf-audiopolicy-iaudiosessionnotification-onsessioncreated),
[регистрация уведомлений](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nf-audiopolicy-iaudiosessionmanager2-registersessionnotification),
[события устройств](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient),
[событие аудиобуфера](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-seteventhandle).

## Ограничения и совместимость

- Windows захватывает **дерево**, включая служебные дочерние exe. Если в нём
  обнаружен явно запрещённый процесс, всё дерево блокируется и это отображается
  в таблице. Точное выделение только родителя этим API не реализовано.
- Обнаружение источников и исключений происходит по уведомлениям аудиосессий,
  а не атомарно с запуском процесса или первой выдачей звука. Это инструмент управления стримом, не граница
  безопасности для конфиденциального аудио.
- До 64 независимых деревьев. Пересекающиеся деревья схлопываются, чтобы один
  и тот же звук не удваивался.
- Добавленные 30 мс могут сдвинуть звук относительно видео. Коррекция видеотайминга
  не реализована.
- Понадобится новое подключение после перезапуска TS (закрыть и открыть панель).
- Перехват зависит от внутреннего устройства клиента. После обновлений TS нужна
  повторная проверка. Установленные файлы клиента не меняются.

## Структура проекта

- `main.py`, `app_runtime.py` — запуск exe, служебный режим и пути ресурсов.
- `audio_router_gui.py` — интерфейс на Tk.
- `router_backend.py`, `mixer_control.py` — событийное управление и отправка изменённых настроек.
- `audio_inventory.py`, `native/audio_inventory.cpp` — подписки Core Audio, имена приложений и завершение процессов.
- `live_policy.py`, `settings_store.py` — выбор приложений и сохранение настроек.
- `live_router.js` — перехват аудиозахвата через Frida.
- `native/router.cpp` — WASAPI-захват и нативное смешивание PCM.
- `silent_clock.py` — молчащий процесс для тактирования потока.
- `build-native.cmd`, `Start Audio Router.vbs` — сборка и запуск.
- `TeamSpeakAudioControl.spec`, `requirements-build.txt` — упаковка в exe.
- `diagnostics.py` — автономная проверка установки без подключения к TeamSpeak.
- `.github/workflows/windows-release.yml` — Windows-сборка и публикация релизов.

Личные настройки (`settings.json`), зависимости (`.venv/`, `.deps/`), сборки
(`build/`, `dist/`) и локальная папка разработки (`_local/`) исключены из Git.
Тесты, исследовательские скрипты и логи остаются только в `_local/` на машине
разработчика и не нужны для сборки или запуска приложения.

## Сборка exe и релизы

После установки средств сборки из раздела выше:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-build.txt
.\build-native.cmd
.\.venv\Scripts\python.exe -m PyInstaller --noconfirm --clean TeamSpeakAudioControl.spec
```

Результат — один файл `dist/TeamSpeakAudioControl.exe` с Python, Tk, Frida,
JS-перехватчиком и нативным микшером внутри. Первый запуск распаковывает ресурсы
и может занять несколько секунд.

Workflow **Windows executable** запускается при push в `main`, pull request
и вручную. Он собирает DLL и exe на Windows, запускает диагностику упакованного
приложения вне исходной папки и сохраняет exe с контрольной суммой в Artifacts.
Диагностика проверяет Tk, нативный микшер, подписки Core Audio, служебный процесс и загрузку Frida/JS/DLL;
она не подключается к TeamSpeak, не воспроизводит и не передаёт звук.

Для публикации обнови `RELEASE_NOTES.md`, закоммить изменения и отправь тег:

```powershell
git tag v0.1.0
git push origin v0.1.0
```

Для следующих версий используй новый тег `v*`. Только после успешной проверки
workflow публикует GitHub Release с `TeamSpeakAudioControl.exe` и `SHA256SUMS.txt`.
Права записи выдаются только задаче публикации; личный GitHub-токен не требуется.

## Если что-то не работает

Проверить комплектность скачанного exe можно без TeamSpeak:

```powershell
Start-Process .\TeamSpeakAudioControl.exe -ArgumentList '--diagnose diagnostics.json' -Wait
Get-Content .\diagnostics.json
```

Это проверка установки, а не слышимости трансляции у зрителя.

- **Нет DLL:** выполни `build-native.cmd` и проверь, что сборка завершилась успешно.
- **Не найден Frida:** установи `requirements.txt` в тот Python, которым запускаешь панель.
- **Не найден TeamSpeak:** запусти один экземпляр клиента, затем нажми «Подключить».
- **Нет управляемого потока:** после подключения панели начни шаринг со звуком заново.
- **Приложения нет в списке:** начни воспроизведение в нём; список обновится по событию новой аудиосессии. При необходимости нажми «Обновить аудиосессии».
- **Галочка не пропускает звук:** проверь exclude, громкость и правило для дерева процессов.
- **После закрытия панели тишина:** перезапусти шаринг, чтобы вернуть обычный захват TeamSpeak.

Для отчёта об ошибке укажи версии Windows и TeamSpeak, шаги воспроизведения
и сообщение из панели. Перед публикацией выдержки из локального журнала проверь
её содержимое: там могут быть сведения о процессах. Сам звук в журнал не пишется.
